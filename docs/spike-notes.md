# Spike notes: one Jev request per file

Measured 2026-09-20 for [#5](https://github.com/mikekelly/s1m/issues/5). Every number below is
from a real call to the TypeSafe API with `model: "jev-latest"`, which answered as
`jev-1.13.0` on every run. The code that produced them is `src/jev.rs`; the files scored are
public and committed — the vendored wiki and this repository's plan — or generated by the
snippet under [How many questions fit](#how-many-questions-fit-in-one-request), so any of these
runs can be repeated.

## How to reproduce

```bash
cargo run -- score-file "how do I cut a release and publish the package" \
  eval/wikis/llm-wiki-manager/wiki/index.md
cargo run -- score-file "how do I cut a release and publish the package" \
  eval/wikis/llm-wiki-manager/wiki/concepts/release.md
cargo run -- score-file "how does s1m decide which links to follow" docs/initial-plan.md
cargo run -- score-file --no-previews "<same query>" eval/wikis/llm-wiki-manager/wiki/index.md
cargo test --test jev_live          # the same three pages, with assertions, needs the key
```

Each command sends exactly one request: the query, the file's path, title and content, and per
link its anchor, sentence, enclosing heading, target path and — unless `--no-previews` — a
preview of the target read from disk (title, frontmatter, first paragraph). The request asks
one Score question for the file and one Noul question per link.

## The API's limits, from the docs

From [Models](https://docs.typesafe.ai/models) and the
[API reference](https://docs.typesafe.ai/api.md), read 2026-09-20:

| Limit | Value |
| --- | --- |
| Endpoint | `POST https://api.typesafe.ai/v1/systemone`, bearer key |
| Price | `jev-1.13`: $0.042 per million input tokens, **output tokens free** |
| Rate limit | 250,000 tokens/second, 1,200 requests/minute; dynamic, may change without notice |
| Context | 64k tokens per request; **32k for `state` plus the longest question** |
| `state` | string, object or array of text; English is the primary language |
| Questions per request | no documented cap; every question sees the same state and is evaluated in parallel |
| Score levels | 2 to 10, ordered |
| Choice options | up to 255 |
| Errors | 401, 422 (validation, names the offending field), 429, 529; retry the last two with backoff and honour `retry-after` |

The 32k figure is the one that binds a file: a hub page's link table grows with its link count,
and the link table is part of the state. `src/jev.rs` caps the file's own content at 40,000
characters (~10k tokens) and each preview's first paragraph at 600 characters, and says so in
the text it truncates. Nothing here converts characters to tokens; four characters per token is
the rule of thumb used to set those caps, not a measurement.

## What one call cost and took

| File | Links | Questions | Input tokens | Output tokens | Latency | Cost | Relevance (score of 3, confidence) |
| --- | --- | --- | --- | --- | --- | --- | --- |
| `wiki/index.md` (hub), previews on | 14 | 15 | 6,919 | 276 | 0.20–0.26 s | $0.000291 | 0.74 (2.23, 0.68) |
| `wiki/index.md` (hub), previews off | 14 | 15 | 3,358 | 276 | 0.21–0.25 s | $0.000141 | 0.79 (2.38, 0.49) |
| `wiki/concepts/release.md` (leaf) | 5 | 6 | 2,893 | 110 | 0.20–0.23 s | $0.000122 | 0.79 (2.38, 0.53) |
| `docs/initial-plan.md` (no links) | 0 | 1 | 3,226 | 20 | 0.22–0.23 s | $0.000135 | 0.99 (2.98, 0.98) |
| synthetic hub, 100 links | 100 | 101 | 25,358 | 1,910 | 0.42 s | $0.001065 | 0.92 (2.76, 0.76) |

One run each; the last column moves by a few hundredths between identical runs, see the
repeat-runs bullet below.

Reading them:

- **Latency is flat.** 15 questions take about as long as 1, and 101 questions take 0.42 s. The
  parallel evaluation the docs promise is real; there is no reason to split a file's links
  across requests on latency grounds.
- **Cost is dominated by the file, then by previews.** A preview costs about 254 input tokens
  here: 6,919 − 3,358 over 14 links, so the title, eight frontmatter fields and a
  200-character paragraph of each target. The floor is not zero — a link with no preview still
  carries its anchor, sentence, heading and question — and the 100-link hub shows the shape:
  25,358 input tokens for 101 questions, about 250 each. At $0.042/Mtok a whole traversal round
  of 25 hub-page-sized files is roughly **$0.007**, and 1,000 such rounds are roughly **$7**.
- **All questions see the same state, so nothing is free to change.** Adding previews moved the
  file's own relevance too (0.74 → 0.79 the other way, confidence 0.68 → 0.49), even though
  the file's text was byte-identical in both runs.

## How many questions fit in one request

The docs cap Choice options and Score levels but not questions per request, so I looked for the
wall with a synthetic hub: one file, 100 links, one generated target page each, so every link
has a real preview.

```bash
mkdir -p /tmp/jev-hub
python3 - <<'PY'
from pathlib import Path
root = Path("/tmp/jev-hub")
lines = ["# Release Hub", "", "A hub page with a hundred outgoing links.", ""]
for i in range(100):
    name = f"page-{i:03d}.md"
    (root / name).write_text(f"# Page {i:03d}\n\nPage {i:03d} covers topic {i:03d} in the release process.\n")
    lines.append(f"- [Page {i:03d}]({name}) — step {i:03d} of the release runbook.")
(root / "hub.md").write_text("\n".join(lines) + "\n")
PY
cargo run -- score-file "how do I cut a release and publish the package" \
  /tmp/jev-hub/hub.md --root /tmp/jev-hub
```

That was accepted in one request: **101 questions, 25,358 input tokens, 0.42 s, no error**. So
there is no question-count wall anywhere near this data — the cost is the state, at roughly
250 tokens per link with previews. The docs' 32k budget for state plus the longest question
therefore binds at **roughly 100–120 links with previews**, and later if previews get shorter
or frontmatter is dropped. The risk row in the plan ("hub pages with hundreds of links may
exceed per-request question or state limits") is real, but it is a token budget problem, not a
question-count problem: chunk the link table or trim previews above ~100 links. [#9](https://github.com/mikekelly/s1m/issues/9)
chunks the questions — see [below](#section-questions-and-splitting-a-file-that-does-not-fit). Every page in
the vendored wiki is far below that (largest: `concepts/repo-layout.md`, 18 links).

I did not push a request over the limit, so the exact failure mode at 32k (422 or truncation) is
untested.

## Section questions, and splitting a file that does not fit

Measured 2026-09-20 for [#9](https://github.com/mikekelly/s1m/issues/9), with the same
`jev-latest` alias. The request now also carries the file's heading sections and asks one Noul
per section — "is the text under this heading, at these lines, useful" — which is what turns a
file's relevance into line ranges. What that costs:

| File | Sections | Links | Questions | Input tokens | Latency | Cost |
| --- | --- | --- | --- | --- | --- | --- |
| `wiki/concepts/release.md` | 2 | 5 | 8 | 3,206 | 0.30 s | $0.000135 |
| `wiki/concepts/node-version-and-types.md` | 8 | 5 | 14 | 5,181 | 0.26 s | $0.000218 |
| `docs/initial-plan.md` (no links) | 17 | 0 | 18 | 5,999 | 0.22 s | $0.000252 |

The plan's own question alone cost 3,226 input tokens before this change, so seventeen section
questions added 2,773 — about **160 tokens a section**, against about 250 for a link with a
preview. Nothing about the shape changed: one request, 0.3 s, and the cost is again the state.

What a section question reads, and what it does not:

- **The heading, its depth and its lines — not the section's text.** The text is already in
  `state.file.content`, and a parent section contains its subsections' text, so copying each
  section's text into its own state entry would multiply the state by the nesting depth. A
  duplicated heading ("See also" appears under several pages) is told apart by its depth and
  lines, and a section of a file long enough to be truncated is judged from its heading alone,
  the way a link with no readable target is judged from its anchor.
- **Both parents and leaves.** A parent owns the prose between its heading and its first
  subsection, which no leaf covers, so judging leaves only would strand it. A parent that is a
  mix of useful and useless subsections lands near the middle of the scale, which is what the
  caller's section threshold is for: on `release.md` the page's own text scored 0.73 and its
  "See also" list 0.14, and on the plan, for the query it is about, "Scoring and pruning" scored
  0.91 while "Sources" scored 0.25.

On splitting, the notes above left the failure mode at the 32k budget untested. It is now
handled the other way round from the suggestion there: **the questions are what get chunked,
not the link table's previews.** The file's content is capped at 40,000 characters already, so
the unbounded part is the question set; a file is posted as many times as it takes, with the
same file in every post, the file's own Score in the first, and the answers merged. A generated
hub of 300 links (302 questions, the shape of the synthetic hub earlier in these notes):

```bash
cargo run -- score-file "how do I cut a release and publish the package" \
  /tmp/jev-hub/hub.md --root /tmp/jev-hub
# call  jev-1.13.0  302 questions in 2 request(s)  83,848 tokens in + 5,822 out  0.58 s  $0.003522
```

Two requests of about 42k tokens each: one request could not have carried them, and the API
accepted both. The split is decided before sending, from the JSON of each part at four
characters per token, with a margin, so it needs no error to trigger it.

## Do target previews earn their tokens

Same page, same query, one run with previews and one without. 14 links, so the two link columns
line up. One pair of runs: the numbers move a few hundredths between runs (see the
repeat-runs bullet below), which does not change the reading.

| Target | Scent with previews | Scent without |
| --- | --- | --- |
| `concepts/release.md` | **0.89** | **0.93** |
| `concepts/dogfooding.md` | 0.86 | 0.10 |
| `entities/commands.md` | 0.12 | 0.43 |
| `concepts/init-command.md` | 0.28 | 0.13 |
| `concepts/template-system.md` | 0.25 | 0.13 |
| `concepts/repo-layout.md` | 0.22 | 0.17 |
| `concepts/unit-tests.md` | 0.16 | 0.13 |
| `raw/raw.md` | 0.06 | 0.21 |
| (the other 6 targets) | 0.10–0.19 | 0.09–0.26 |

Without previews the release page stands far above everything else, and every other page sits at
0.43 or below. With previews the release page is still first, but `concepts/dogfooding.md`
follows it up at 0.86 — that jump is the whole story, below. The previews roughly double the
input tokens (6,919 vs 3,358, $0.00015 a call) and change nothing about latency.

What the previews changed is the middle of the list. `concepts/dogfooding.md` went from 0.10 to
0.86 — the anchor "Dogfooding" says nothing about releasing, but the target's own frontmatter
names `concepts/release.md` in its `related:` list and its summary is about shipping and
validating the tool. `entities/commands.md` moved the other way, 0.43 to 0.12, once the model
could see the page is about `src/commands/`. Only the top of the list is the same either way.

**Verdict: keep the previews.** They are the only signal that separates a page which says
nothing from a page whose own links point at the answer, and at $0.0003 a call the tokens are
not the constraint. Two caveats for later stages:

- The preview is the single biggest knob on the link ranking, so a `--threshold` tuned with
  previews on is not valid with them off. #10's modes should fix the preview policy rather than
  leave it to the caller.
- The frontmatter is the part most likely to mislead: `related:` and `tags` make every page look
  connected to every other, and three pages in this wiki name `concepts/release.md` there. Only
  `dogfooding.md` moved much, so frontmatter alone does not explain the jump — this run varied
  the whole preview as one knob and cannot say which part did the work. Worth splitting in a
  later experiment (title + paragraph versus frontmatter included).

## Is a Score right for file relevance, or is a Noul enough

**Keep the Score.** Three reasons, from the runs:

1. The output the plan wants is ordered, 0 to 1, and sorted by relevance. A Score answers
   directly on that scale: it is a probability-weighted position over the four levels, so it
   can sit between levels (2.23 of 3 on the hub page) rather than forcing a yes or a no.
2. A Noul's 0.5 means the model is unsure, not that the file is middling — the docs are
   explicit about this, and it makes a probability a poor ranking key when both "unsure" and
   "half-relevant" map to the same number. A Score carries `confidence` separately, and it did
   work here: 0.99 for the plan against a query the plan is about, 0.51 for a leaf page whose
   whole content is a pointer to a runbook kept elsewhere. That 0.51 is the right kind of
   signal for #7 to gate on.
3. The four levels the issue names (central / supporting / tangential / unrelated) are the
   plan's own table, and they are what makes the hub page's 0.74 comprehensible:
   "supporting" — the index is not the answer, but its links are.

The Noul stays where the question is genuinely yes/no: one per link, "is following this likely
to lead somewhere useful". A Score there would invent levels the traversal does not need; a
threshold on a probability is exactly what the frontier wants.

The plan's other open question — score very long files by section only, skipping the whole-file
judgment — is not answered here. One datapoint: this repository's 11 KB plan scored 2.98–2.99
of 3 with 0.98–0.99 confidence as a whole file for a query it is about, so the whole-file
judgment is sound at that size. [#9](https://github.com/mikekelly/s1m/issues/9) answered it by
keeping the whole-file Score and adding section scores beside it: the file Score is what ranks
the reading list, and a section-only number would mix a best paragraph against another file's
average in one column.

## What else the runs showed

- **Jev is stable, not deterministic.** The same request sent three times (identical state,
  6,919 input tokens each time) returned the same top two links and the same wide gap below
  them, but the numbers move: `concepts/release.md` 0.89 / 0.90 / 0.88,
  `concepts/template-system.md` 0.25 / 0.21 / 0.30, file relevance 0.74 / 0.74 / 0.75
  (confidence 0.67 / 0.68 / 0.65). Ordering below the top few shuffles with them. The plan's
  determinism goal therefore has to come from the cache in
  [#7](https://github.com/mikekelly/s1m/issues/7), not from the model: same content, query and
  mode must mean same answer, which only a cache can promise.
- **The same target can appear twice in one file.** `concepts/release.md` links
  `node-version-and-types.md` twice (once in prose, once in "See also") and `dogfooding.md`
  twice, and each copy was judged separately with near-identical scents (0.43 / 0.43 and
  0.18 / 0.14). Traversal must dedupe links by target, or it will queue and score the same page
  twice.
- **File relevance and link scent do separate.** The hub page scored 0.74 — supporting, not
  central — while its links ranged from 0.06 to 0.89. Nothing here suggests pruning a file's
  links because the file scored low, which is what the plan expects of index pages.
- **Nothing is read about a link whose target is unreadable, and it is judged anyway.** Links
  that escape the root, and links to files that do not exist, carry no preview — a root escape
  is content outside what the caller asked about, and a broken link has nothing to read — and
  are still asked about and judged from their anchor, sentence and heading. That is deliberate,
  and it is what the fixture tests assert.

## Not settled by this spike

- Calibration. No gold set, so nothing here says whether scent 0.89 is *right*, only that it is
  clearly above 0.16 on the same page. The default `--threshold` needs
  [#9](https://github.com/mikekelly/s1m/issues/9)/evaluation, not this data.
- Whether splitting a file's questions across requests is better than trimming its previews, past
  the measurements [#9](https://github.com/mikekelly/s1m/issues/9) took: a split keeps every
  answer at full fidelity, and costs a second round trip for the same file.
- Whether the Score's four levels beat a different number of levels, or beat a Noul plus a
  second "is it even on topic" question. One run per page is not enough to tell.
